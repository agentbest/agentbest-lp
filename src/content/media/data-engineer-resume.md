データエンジニアの職務経歴書は、一般的なエンジニア向けの書き方では通過率が上がりにくい。採用担当者がデータエンジニアのレジュメを評価する際、技術スタックの列挙だけでなく「どのようなデータ基盤をどのような規模で設計・運用したか」「ビジネス側にどのような価値をもたらしたか」を重視する傾向があるためだ。本記事では、書類通過率を高めるための構成原則から各セクションの記述方法、実例の型まで体系的に解説する。

---

## データエンジニアの職務経歴書が難しい理由

データエンジニアという職種は、フロントエンドやバックエンドエンジニアと比べて「何をアウトプットとして示すべきか」が分かりにくい。コードはサービス機能として直接ユーザーに届くが、データパイプラインやデータウェアハウスは社内インフラであり、外部から可視化しづらい。

この構造的な難しさが、職務経歴書の記述に二つの問題を生む。

**問題1：技術スタックの羅列になりやすい**
BigQuery、Airflow、dbt、Spark――ツール名を列挙するだけでは、採用担当者はその人の「設計力」「問題解決の深さ」「スケールの経験値」を判断できない。

**問題2：成果が抽象的になりやすい**
「データ基盤を構築した」「パイプラインを改善した」という記述は、規模感・難易度・インパクトが伝わらない。ビジネス職の「売上を〇〇億円達成」に相当する定量表現をデータエンジニア的に置き換えることが必要になる。

## 書類審査で評価される3つの軸

採用担当者がデータエンジニアの職務経歴書を読む際、主に以下の3軸で評価する傾向がある。

| 評価軸 | 確認されること | 記述のポイント |
|---|---|---|
| **技術的深度** | 特定技術を使いこなしたか、設計判断できるか | ツール名＋採用理由・設計方針まで記述 |
| **スケール感** | データ量・処理件数・関与人数の規模 | GB/TB/PB、日次件数、利用者数を明記 |
| **ビジネス貢献** | データ基盤がどの意思決定を支えたか | 利活用先・削減コスト・短縮時間を記述 |

この3軸を意識して各プロジェクト記述を組み立てることが、他候補者との差別化につながる。

## 職務経歴書の基本構成

データエンジニアの職務経歴書は、以下の構成が標準的かつ評価されやすい。

### 1. キャリアサマリー（5〜8行）

職務経歴書の冒頭に置く自己紹介の要約。採用担当者が最初に読む部分であり、ここで「どんな人材か」の印象が決まる。

記述すべき内容は3点に絞る。
- 総経験年数と主な技術領域（データ基盤構築、ETL設計、分析基盤など）
- 扱ってきたデータ規模・業界の傾向
- 強みの方向性（設計寄り・運用改善寄り・ビジネス連携寄りなど）

**記述例（構造の型）**
> データエンジニアとして5年のキャリアを有する。ECおよびSaaS領域において、日次数億レコード規模のデータパイプライン設計・構築を担当。クラウドデータウェアハウスを中心としたアーキテクチャ設計を得意とし、データ品質管理の仕組み整備やビジネスサイドとの要件定義にも継続的に携わっている。

### 2. スキルマトリクス

技術スタックは「カテゴリ分類＋習熟度の目安」で示すと読みやすい。

| カテゴリ | 主要技術・ツール | 習熟度の目安 |
|---|---|---|
| クラウド | AWS (Redshift, Glue, S3), GCP (BigQuery, Dataflow) | 実務設計経験あり |
| バッチ処理 | Apache Spark, Apache Airflow, Digdag | 本番環境での運用経験あり |
| ストリーミング | Apache Kafka, Kinesis | 検証・実装経験あり |
| データ変換 | dbt, SQLMesh | チーム導入・設計経験あり |
| プログラミング | Python, Scala, SQL | 業務レベルで継続使用 |
| データ品質 | Great Expectations, dbt tests | 導入・運用経験あり |
| IaC / CI-CD | Terraform, GitHub Actions | 実務経験あり |

習熟度は「業務で使用した」「設計判断をした」「チームに展開した」など具体的な経験の粒度で表現するほうが、「上級・中級・初級」より採用担当者に正確に伝わる。

### 3. 職務経歴（プロジェクト単位で記述）

最も重要なセクション。企業単位ではなく**プロジェクト単位**で記述することを推奨する。一社に複数プロジェクトがある場合は、インパクトの大きいものを2〜3件ピックアップして詳述する。

各プロジェクトの記述フォーマットは以下の型を基本にする。

```
【プロジェクト名 / 在籍期間】
業種・事業規模の背景（1〜2行）
- 担当フェーズ：要件定義 / 設計 / 実装 / 運用 / 改善
- データ規模：日次〇〇件、テーブル数〇〇本、利用者数〇〇名
- 使用技術：（具体的なスタック）
- 課題と対応：〇〇という課題に対し、〇〇の設計方針を採用
- 成果：処理時間を〇〇分から〇〇分に短縮 / 障害件数を月〇〇件から〇〇件に削減 等
```

## ケーススタディ：通過率が変わった記述の改善例

以下は、同じ経験を持つ候補者の「改善前」と「改善後」の記述例だ。

### 改善前（通過しにくい記述）

> 社内のデータ基盤をBigQueryとAirflowを使って構築した。ETLパイプラインを整備し、分析チームが使いやすい環境を用意した。

この記述の問題点は、規模・難易度・インパクトがすべて不明であること。採用担当者からすると、「どの程度の経験か判断できない」という評価にとどまりやすい。

### 改善後（通過しやすい記述）

> **EC事業部向けデータウェアハウス構築（2022年4月〜2023年3月）**
>
> 日次3,000万レコード規模のトランザクションデータを処理する分析基盤を0から設計・構築。従来はアドホックなBigQueryクエリが乱立し、定義の不統一・重複集計が恒常化していた状態を解消するため、dbtによるモデリング層を導入してデータの定義管理を一元化した。
>
> - データ規模：日次約3,000万レコード、マート数120本
> - 担当範囲：要件定義〜設計〜実装〜運用体制整備まで一貫して担当
> - 使用技術：BigQuery, Airflow (Cloud Composer), dbt, Terraform, Python
> - 成果：レポート作成工数を週平均8時間から1.5時間に短縮。データ定義の問い合わせ件数が月平均30件から5件以下に減少。障害起因の集計誤りをゼロに低減

改善後は、背景・課題・技術選定の意図・定量成果が一体になっており、採用担当者が候補者の経験値を具体的にイメージしやすい構成になっている。

## 年収レンジと経験年数の目安

職務経歴書の内容が採用可否だけでなく、提示年収の幅に影響することを念頭に置いておくと、何をアピールすべきかの優先順位が整理しやすい。

| 経験年数の目安 | 担当できる領域の傾向 | 年収レンジの目安（東京・事業会社） |
|---|---|---|
| 1〜3年 | 既存パイプラインの改善・運用、ETL実装 | 450万〜650万円程度 |
| 3〜5年 | 新規基盤設計・構築、チームリード補佐 | 650万〜900万円程度 |
| 5〜8年 | アーキテクチャ設計、チームリード、経営層への連携 | 900万〜1,200万円程度 |
| 8年以上 | 組織横断データ戦略、データプラットフォームPM | 1,200万円〜 |

上記はあくまで目安であり、業種・企業規模・スキルの希少性によって大きく変動する。職務経歴書でスケール感と設計力を示せるかどうかが、同年次での提示年収の分かれ目になりやすい。

## よくある質問

**Q. OSS・個人開発の経験は職務経歴書に記載すべきですか？**

業務経験を補完する形であれば記載は有効です。ただし、技術的な意図と得られた学びを簡潔に記述することが前提です。「〇〇というOSSにコントリビューション済み（PRリンク）」や「個人でデータパイプラインを構築し、〇〇を検証した」のように、事実と目的を明確に書くと評価されやすい傾向があります。

**Q. クラウドの資格（AWS・GCP認定等）はどの程度評価されますか？**

資格は「一定の知識体系を体系的に習得した」というシグナルとして機能しますが、実務経験の代替にはなりません。資格欄に記載しつつ、対応するプロジェクト記述と連動させることで説得力が増します。資格単独では判断材料として限定的と見なされるケースが多い印象です。

**Q. データエンジニアとデータサイエンティストの兼務経験がある場合、どう整理すればよいですか？**

応募ポジションに合わせてどちらの軸を前に出すかを決めることが重要です。データエンジニアポジションへの応募であれば、パイプライン設計・基盤構築の記述を主軸に置き、分析・モデリングの経験は「連携・協働の文脈」として補足する構成が適切です。両方を均等に書くと、専門性が曖昧に見えるリスクがあります。

**Q. 在籍期間が短い案件（6ヶ月未満）は記載を省くべきですか？**

技術的に意義のある経験であれば、在籍期間が短くても記載する価値があります。ただし、複数の短期案件が連続する場合は「業務委託としてプロジェクト型で従事」などコンテキストを説明する一文を加えると、キャリアの一貫性が伝わりやすくなります。

## まとめ

データエンジニアの職務経歴書で書類通過率を高めるためには、技術スタックの列挙から脱して「データ規模・設計判断の背景・ビジネスへの貢献」を一体として記述することが求められる。プロジェクト単位での記述、定量成果の明示、ツール選定の意図の言語化という3点を実践するだけで、読み手の解像度は大きく変わる。スキルマトリクスは習熟度を経験の粒度で表現し、キャリアサマリーで全体像を最初に示す構成が有効だ。職務経歴書の内容は採用可否だけでなく提示年収にも影響するため、自身の経験を適切に言語化することは市場価値の可視化と直結する。現職での経験が正しく評価されているか確認したい場合は、キャリアの棚卸しを専門家に相談することも一つの選択肢になる。
