## 採用担当者がバックエンドエンジニアの職務経歴書で見ているポイント

### 技術スタックの「深さ」と「文脈」

バックエンドエンジニアの選考において、採用側は技術スタックの羅列よりも、「その技術をどのような判断のもとで選定・活用したか」に注目しやすい。たとえば「Go・PostgreSQL・Kubernetes使用」という記述と、「マイクロサービス化に伴うAPIゲートウェイの刷新において、スループット要件を満たすためGoを採用し、PostgreSQLのパーティショニングで大規模テーブルのクエリ応答を改善した」という記述では、読み手が受け取る情報量が大きく異なる。

使用した技術を列挙する際は、その技術を選んだ理由・適用した課題・得られた効果の三点をセットにする意識が重要である。

### スコープの明確化：個人貢献か、チームへの関与か

「システムを改善した」という記述は、個人が主導したのか、チームの一員として参加したのかが伝わらない。採用側は応募者のオーナーシップと責任範囲を把握したいため、以下のように役割を明示する。

- 「バックエンドチーム5名中、APIサーバー設計を担当」
- 「スクラムチーム8名のうち、データ基盤構築を主導（PM・インフラエンジニアと連携）」

こうした記述によって、実務上のコミュニケーション範囲や技術的なオーナーシップが具体的に伝わる。

### 定量的な成果の記述

バックエンドエンジニアの成果は、フロントエンドと比較してビジネス指標との直結が見えにくい場合があるが、技術的な指標（レイテンシ・スループット・可用性・リリース頻度など）を用いて定量化することが可能である。成果として記述しやすい指標の例を以下に示す。

| 指標の種類 | 記述例 |
|---|---|
| パフォーマンス | APIレスポンスタイムを平均1,200msから200ms以下に改善 |
| スケーラビリティ | ピーク時リクエスト数を月500万→月3,000万件に対応 |
| 可用性 | 障害発生頻度を月3〜5件から月0〜1件に削減 |
| 開発効率 | デプロイ頻度を月1回から週3回に向上（CI/CD整備） |
| コスト | クラウドインフラ費用を月次で約30%削減 |
| チームへの貢献 | コードレビュー文化の導入によりバグ検出率を向上（QAフェーズでの不具合件数を半減） |

すべての成果に数値が求められるわけではないが、少なくとも2〜3項目は定量化を目指すと説得力が増す。

## 職務経歴書の構成と各セクションの書き方

### 推奨する全体構成

バックエンドエンジニアの職務経歴書は、以下の構成が標準的に機能しやすい。

1. **職務要約（3〜5行）**：キャリアの核心と強みを簡潔に記述
2. **スキルサマリー**：言語・フレームワーク・インフラ・ツール類を整理
3. **職務経歴（逆年代順）**：プロジェクト単位で記述
4. **保有資格・学習活動**（任意）

### 職務要約の書き方

職務要約は採用担当者が最初に読む箇所であり、「この人が何のエンジニアで、何ができるか」を10秒以内に把握できることが理想である。

**記述の型：**
> 〔経験年数〕年のバックエンド開発経験を持ち、〔主要技術領域〕を得意とする。〔主な実績・専門性〕を強みとしており、〔志向・次のキャリアで実現したいこと〕を目指している。

**記述例：**
> バックエンド開発を中心に7年の経験を持ち、Go・Java・AWSを用いたサービス設計・運用を得意とする。スタートアップ期から成長期にかけてのシステムアーキテクチャ刷新を複数回経験しており、高トラフィック環境における安定稼働の設計に強みがある。今後はプラットフォームエンジニアリング領域への関与を深めたい。

### スキルサマリーの記述方法

スキルは一覧としてまとめ、応募先の技術スタックとの対応を意識して並べると可読性が高まる。単に列挙するだけでなく、経験年数や習熟度の目安を添えると採用側の判断が容易になる。

| カテゴリ | スキル・ツール | 経験年数の目安 |
|---|---|---|
| 言語 | Go / Java / Python | Go：5年 / Java：7年 / Python：2年 |
| フレームワーク | Spring Boot / Echo / FastAPI | Spring Boot：4年 |
| データベース | PostgreSQL / MySQL / Redis / DynamoDB | PostgreSQL：6年 |
| インフラ | AWS（EC2・RDS・Lambda・ECS）/ Terraform | AWS：4年 |
| ミドルウェア | Apache Kafka / RabbitMQ | Kafka：2年 |
| 開発手法 | スクラム / GitHub Actions / Docker / Kubernetes | – |

- **背景と課題**：注文処理の急増（月次約300万件→700万件）に伴い、既存のモノリシックAPIでレイテンシが悪化。ピーク時のエラー率が3%を超える状況が発生していた。

  - デプロイ時間の短縮（平均45分→8分）

## 経験年数別の強調ポイント

職務経歴書の内容は、経験年数によって重点を置くべき観点が異なる。

| 経験年数の目安 | 強調すべきポイント | 注意すべき点 |
|---|---|---|
| 1〜3年（ジュニア〜ミドル初期） | 習得技術の広さ、自走力、コードレビューへの参加 | 担当範囲の過剰な拡大表現を避ける |

## よくある質問

**Q1. 使用したことがある技術はすべて記載すべきでしょうか？**

経験の浅い技術まで網羅的に列挙すると、面接で問われた際に対応できないリスクが生じる。目安として、実務で継続的に使用した期間が3〜6ヶ月以上の技術を中心に記載し、学習中・触れた程度のものは「学習中」として分けて記述するか、省略する判断が適切な場合が多い。

**Q2. 守秘義務があってプロジェクトの詳細が書けない場合はどうすればよいですか？**

事業内容や固有名詞を抽象化する形で記述することが一般的である。「大手通信キャリア向けの決済システム開発」「月間アクティブユーザー数百万規模のtoC向けサービス」のように、規模感や領域が伝わる範囲で記述する方法が有効である。技術的な課題・施策・成果の構造は守秘義務に抵触しない範囲で具体的に保つことが望ましい。

**Q3. 年収交渉に有利な職務経歴書の書き方はありますか？**

年収の評価は市場における希少性・難易度・成果の三軸で決まる傾向がある。特定技術の深い専門性（例：分散システム設計、大規模データ基盤の構築経験）や、ビジネスに直結した定量的成果を明確に記述することで、希少性と成果の両軸を示せる構成が評価されやすい。スキルサマリーと職務詳細の記述が整合していることも重要である。

**Q4. 転職回数が多い場合、職務経歴書でどのように見せればよいですか？**

各在籍期間において「その会社で何を達成したか」を具体的に示すことが前提となる。加えて、職務要約の段階でキャリアの軸（例：「一貫してデータ基盤構築に携わってきた」「スタートアップのグロースフェーズに特化してきた」）を明示すると、転職経歴の文脈が伝わりやすくなる。

## まとめ

バックエンドエンジニアの職務経歴書で差がつくのは、技術スタックの量ではなく、「何を解決したか」「それによってどのような成果が得られたか」の記述の精度である。職務要約・スキルサマリー・プロジェクト詳細の三層をそれぞれ整合させ、採用担当者と技術面接官の双方が読める構成にすることが基本方針となる。定量的な成果・役割の明確化・技術選定の文脈という三点を意識するだけで、同じ経験でも書類の印象は大きく変わり得る。経験年数に応じた強調ポイントのズレを修正するだけでも、通過率の改善につながる場合がある。現在の職務経歴書が自分のキャリアを適切に表現できているか不安を感じる場合は、業界・職種の実情を知るキャリアアドバイザーへの相談を検討する価値がある。
